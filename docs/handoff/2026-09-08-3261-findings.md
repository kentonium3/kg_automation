## Findings (most consequential first)

### F-6 — Implement-path wedge: lane allocation conflicts on spec-kitty's own status files, remediation impossible as printed, then blocked by lane sparse-checkout ⚠ pre-existing (best judgment), most serious

**Sequence** (throwaway repo, mission `g-arc-01M218EX`, planning artifacts
committed on `feat/g-arc` — where the specify guard itself says they must land):

1. `spec-kitty agent action implement WP01 --agent claude --mission g-arc-01M218EX`
   → **exit 1**. It creates the lane branch, then:
   `Workspace allocation failed: cannot auto-merge the recorded planning commit
   '8b50f5b…' into lane 'lane-a': the merge conflicts. merge … into the lane
   'lane-a' worktree manually, resolve the conflicts, commit, then re-run …`
   **At this moment no lane worktree exists** (`git worktree list`: primary +
   coord only) — the printed remediation is impossible when printed.
2. Identical retry → **exit 1**, same error, **but now the lane worktree gets
   created** (`.worktrees/g-arc-01M218EX-lane-a`). Non-idempotent debris
   accretion, though it converges and makes step 1's advice retroactively
   possible. The retry also re-commits planning artifacts to the coordination
   branch.
3. The conflicts are in **spec-kitty's own bookkeeping** —
   `status.events.jsonl` + `status.json` — because the tool committed divergent
   copies on the feature branch (via `agent tasks finalize-tasks` bootstrap +
   its own guidance to commit dirt, F-9) and on the coordination branch (via
   `agent mission finalize-tasks`). The operator is told to hand-resolve an
   event log that doctrine says only the workflow may write.
4. Following the remediation in the lane worktree: `git merge 8b50f5b`
   conflicts as predicted; after resolving (event-id union + snapshot rebuild),
   **`git add` refuses** — the lane worktree is a **sparse checkout that
   excludes `kitty-specs/`** ("matched paths that exist outside of your
   sparse-checkout definition"). The prescribed recovery is structurally
   blocked by the lane's own sparsity rules; only `git add --sparse` (git
   surgery the CLI never mentions) unblocks it.
5. After `--sparse` commit: implement dispatch → **exit 0**, WP01 claimed, lane
   workspace live. So the arc *can* continue, but only past two contradictory
   failures and manual event-log surgery.

**Reproduces:** step 1→2 behavior reproduced exactly (two consecutive runs).
**Hotfix or pre-existing:** pre-existing, with reasonable confidence: none of
the four hotfix items touch lane allocation/sparse-checkout, and
"lane branches reject kitty-specs" is a known 3.2.4-era gotcha in my project
memory. Not a reason to hold 3.2.6.1; very much a reason to file against the
implement path.

### F-1 — G-1 answered: create-after-success is silently non-idempotent (new folder every time)

`agent mission create g-arc` repeated identically after a **successful** create:
every invocation → **exit 0**, a **new** `kitty-specs/g-arc-<newULID>` folder,
a new coordination branch, a new scaffold commit — and **no signal** that
same-named missions already exist. 3 runs → 3 missions, in both setups (6/6).
Debris per run: one committed scaffold, one branch, one untracked `spec.md`
(the #846-designed state). Refuse/reuse/second-folder? — **second folder,
silently.**
**Hotfix or pre-existing:** pre-existing design — ULID-suffixed slugs
deliberately support concurrent same-named missions (`branch_naming.py:22`), so
create cannot distinguish "retry" from "intentional sibling". The `#4033`
failure-path guards are working; the success-path retry simply has no guard.
Worth a warning ("N existing missions share this base slug") rather than a
block.

### F-7 — Two `finalize-tasks` commands; the discoverable one doesn't produce what implement demands

`spec-kitty agent tasks finalize-tasks` (discoverable under the tasks group an
agent is already using) exits 0, injects dependencies, seeds WP events — but
writes **no `lanes.json`**. `agent action implement` then fails with
"lanes.json is required … Run the task-finalization step", which names no
command. The one that actually computes lanes is **`agent mission
finalize-tasks`** (found only by reading the `/spec-kitty.tasks-finalize` shim).
An agent that ran "the" finalize and is told to run "the task-finalization
step" it already ran is in a loop. Also: running the `agent tasks` variant
first is what seeded status events on the feature branch — a direct
contributor to F-6's divergence.
**Pre-existing** (command topology, not hotfix surface).

### F-8 — Ownership auto-inference generates metadata that fails its own validation, non-atomically

First `agent mission finalize-tasks` run: **exit 1** with
`WP01: authoritative_surface 'tests/test_greet.sh/' is not a prefix of any
owned_files entry: ['tests/test_greet.sh']` — the tool *itself* inferred that
`authoritative_surface` (a file path + trailing slash) and those `owned_files`,
then rejected its own inference. For WP02 (a README-only WP) it confabulated
`authoritative_surface: src/` / `owned_files: [src/**]` out of nothing. On
exit 1 both WP files are left **modified-uncommitted** (the failed run's
inferred frontmatter written to disk) — a non-atomic failure, which is the
hotfix's own theme, here in finalize. **Reproduces identically** on retry.
After hand-correcting the frontmatter, validation is otherwise reasonable
(literal paths must exist or be in `create_intent`; globs only warn) and
finalize completes: lanes computed, acceptance-matrix scaffolded, committed
(though `status.events.jsonl` is again left modified-uncommitted after the
"Tasks committed" success message).
**Pre-existing** (ownership machinery is not in the hotfix's four items).

### F-9 — `record-analysis` is blocked by spec-kitty's own byproducts

`agent mission record-analysis --input-file -` → **exit 1**:
`Refusing to record analysis report with pre-existing dirty working tree`,
listing `kitty-ops/lifecycle.jsonl` (written by spec-kitty's own dispatch) and
the **sibling missions'** untracked `spec.md` scaffolds — the exact state
`mission create` deliberately leaves per #846
(`uncommitted_artifacts: populated and committed later`). One spec-kitty
command's designed output blocks another spec-kitty command, across missions.
In a many-mission repo any scaffold-stage sibling would block every other
mission's analysis recording. Cleared by committing the dirt.
**Pre-existing** (dirty-tree discipline, not hotfix surface).

### F-10 — `next --result success` skips implement's gates and desyncs FSM from lanes

At mission state `implement`, `spec-kitty next --agent claude --result success`
advanced the **mission FSM to `review`** while: no analysis-report gate, no
lanes.json gate, no lane worktree, zero implementation artifacts, and the
kanban (`agent tasks status`) still showing **both WPs in Planned**. The same
gates are enforced (hard, exit 1) on the `agent action implement` path. So the
two drive surfaces disagree about what implement requires, and an agent
reporting optimistic `--result success` can walk the FSM to review with
nothing built and the event log contradicting the FSM.
(Also observed en route: with WPs unfinalized, `next --result success`
advanced tasks→implement then returned `kind=blocked,
reason="No action mapped for WP step 'implement'"` — which recovered after
proper finalize, so likely just a rough edge of the same gap.)
**Pre-existing** (composition/`next` path; adjacent to #3909's territory).

### F-2 — Doubled ULID in every teardown message (cosmetic)

Every `mission close --discard` prints
`✓ Coordination worktree torn down for <slug>-<ULID_repeated>` — e.g.
`g-arc-01M218EX-01M218EX`. 3/3 discards, both setups. The teardown itself is
correct (C-4); only the message mangles the slug. Echoes the "eats the
mission #, prints success" Slack flavor but here it's display-only.
**Pre-existing** (teardown message path; probably worth 1 line in a filed
issue).

### F-3 — Rich markup leaks into implement output (cosmetic)

Successful implement dispatch prints a literal
`[dim]Baseline: 1 pre-existing test failure(s) captured[/dim]`.
